# FFXIV real-time foot IK — feasibility, options, roadmap, and spike plan

## Context

FFXIV does not place feet on terrain: on slopes and steps the uphill foot clips into the ground and the downhill foot floats. The idea is a Dalamud plugin that, every frame, reads the animated leg bones, asks the game's collision system where the ground is under each foot, and bends the legs so both soles rest on it. Warcry (`D:\dev\ffxiv-skill-voicelines`) is the reference for project setup and conventions. `D:\dev\ffxiv-real-time-ik` is empty; this session leaves a roadmap document and a buildable spike that proves the two real unknowns (the hook survives to render; collision height is usable) before any IK math is written.

Decisions taken with the user (2026-09-10): local player first, code shaped to extend to other characters later; deliverable is roadmap + spike; post-core priorities are slope-aligned feet, stairs/ledges, sitting/emotes. Plugin compatibility is lower priority but must never crash.

## Feasibility verdict

Feasible. Every building block has a shipping precedent in gameplay, and the novel part is glue plus ~100 lines of math.

| Need | Verified availability (FFXIVClientStructs 7.55 / Dalamud 15.0.3 / .NET 10, checked against the installed dev assemblies) |
|---|---|
| Read/write the animated pose | `hkaPose`: `ModelPose`, `LocalPose`, `ModelInSync`, `LocalInSync`, `SyncModelSpace()`, `AccessBoneModelSpace(idx, PropagateOrNot)`. `hkaSkeleton`: `Bones[].Name`, `ParentIndices`, `ReferencePose`. Path: `Character*` → `DrawObject` (check `GetObjectType()==CharacterBase`) → `Skeleton` (has `Transform` pos/rot/scale, `PartialSkeletonCount`) → `PartialSkeletons[0].GetHavokPose(0)`. |
| Ground under a point | `BGCollisionModule.RaycastMaterialFilter(origin, dir, out RaycastHit, maxDist)` static wrapper, world space, `RaycastHit.Point/Normal/Distance/Material`. `SweepSphereMaterialFilter` exists too (stairs). |
| Move the whole character vertically | `GameObject.DrawOffset` (+ `SetDrawOffset`), the field SimpleHeels uses for heel height. Fallback: CustomizePlus's `GameObject_UpdateVisualPosition` hook (sig verified below). |
| Post-animation, pre-render hook | Not in ClientStructs; signature scan. CustomizePlus `RenderManager::Render` sig (verified from their `main`), proven for every visible character in gameplay. Brio's per-skeleton `UpdateBonePhysics` sig as documented fallback only (GPose-only precedent, may run on job threads). |
| State gating | `Character.Mode` (`CharacterModes`: None=0…Performance=16; Normal, Dead, EmoteLoop, Mounted, Crafting…), `IsJumping()`, `IsMounted()`; Dalamud `ICondition` (Jumping, Mounted, Swimming, Diving, InFlight, WatchingCutscene, BetweenAreas), `IClientState.IsGPosing`. |
| IK solver | Not exposed. Own analytic two-bone solver in System.Numerics (~40 lines). Brio/Ktisis sig the Havok solvers; more fragile than the math. |

Costs that are real:
- **Signature maintenance** each patch. One constants file, hook failure logged and inert (Warcry pattern), CustomizePlus republishes sigs within days.
- **No "foot planted" tag from the game.** Height-above-rest heuristic, tunable. Core placement is vertical only, so a wrong planted guess cannot slide a foot horizontally. The two horizontal moves added later are bounded differently: gathering only moves a foot that is already hanging over an edge (since 2026-09-11 both feet are placed together: rays fan out from each ankle, and the cheapest pair of standable samples a stance apart and uncrossed wins, so no axis heuristic decides side by side against front to back), and the wall push (2026-09-11) moves a planted foot by the smallest amount that takes its footbox out of a wall, recomputed from the animation each frame rather than accumulated, so it cannot drift, and eased over 0.1 s so it cannot pop.
- **Collision ≠ visual mesh.** Stairs are often ramps in collision; some props have none. Stairs get their own milestone.
- **Access violations are not catchable in .NET.** Pointer, type and bounds guards before every dereference; `try/catch` only covers managed math bugs.

## Design

### Where the work runs

Everything (gate, raycasts, draw-offset write, IK) runs inside the `RenderManager::Render` detour on the main thread, once per frame, with a Stopwatch `dt`. Edits are written **before** calling `Original` (as CustomizePlus does). Nothing is done in `Framework.Update` except in the M0 spike (read-only overlay).

```
RenderHookAddress   = "E8 ?? ?? ?? ?? 48 81 C3 ?? ?? ?? ?? BF ?? ?? ?? ?? 33 ED"   // RenderManager::Render
MovementHookAddress = "E8 ?? ?? ?? ?? 84 DB 74 3A"                                  // GameObject_UpdateVisualPosition (fallback only)
delegate nint RenderDelegate(nint a1, nint a2, nint a3, int a4);
```
Resolve with `ISigScanner.TryScanText` (these are `E8` call sites, ScanText resolves the target) and `IGameInteropProvider.HookFromAddress`.

Failure containment: `Original` always called and never inside our try; detour body = `if (armed) try { Tick(); } catch { armed=false; faults++; log once }`; guards before every deref (Character, DrawObject, object type, Skeleton, `PartialSkeletonCount>0`, pose, `pose.Skeleton`, `ModelPose.Length == Bones.Length`, every index in range); `float.IsFinite` on every output before any write, else skip the frame; breaker re-armed only from the UI; `Dispose` unhooks **and** removes our draw-offset delta so the character is not left sunk, and the breaker tripping removes it too (a tripped Tick never reaches the offset write again).

## Feature options and recommendation

| Option | Recommendation | Why |
|---|---|---|
| Local player vs all characters | Local first; `Tick` written over a list of targets from day one | Extension is an object-table filter, a radius, per-character state, and a frame budget |
| Own solver vs game Havok solver | Own analytic two-bone | 40 lines, no sig, no struct-layout risk |
| Foot raise only vs pelvis drop | Both; pelvis drop is its own milestone via `DrawOffset` | Raise-only fixes clipping but not floating |
| Foot rotation to normal | M4, ±30° clamp, weighted by `p·w` | User priority; cheap once write-back works |
| Stairs/ledges | M5: heel/toe rays per foot, hysteresis, sphere sweep if needed | User priority; collision ramps mean partial wins |
| Sitting/emotes | M6: `EmoteLoop` whitelist; ground-sit is a root tilt to the normal, not leg IK | User priority; different problem than standing |
| Other players/NPCs | M7, opt-in radius + budget | Same code path plus per-character state |
| Compat (CustomizePlus, SimpleHeels, Brio/Ktisis) | GPose gate from M1; `DrawOffset` delta-only writes; observe CustomizePlus ordering in M7 | Must not crash; cooperation later |
| Distribution | Self-hosted third-party repo `github.com/BSoD38/dalamud-plugins` (shared with Warcry; the pluginmaster URL is permanent once users add it), csproj is the manifest. Release = `dotnet build -c Release`, then `publish.ps1 FootIk\bin\Release\FootIk` in that repo | No D17 constraints |

- **The icon has to be inside the zip.** Reported and fixed 2026-09-15: the icon showed in the plugin list and vanished once the plugin was installed. Dalamud takes an installed plugin's icon from `images\icon.png` beside the DLL and only falls back to a URL — both literals (`icon.png`, and `images/{2}` for the remote form) are in `Dalamud.dll` next to `GetPluginIconFileInfo`, read out of the assembly rather than assumed. DalamudPackager deliberately keeps `images\` **out** of `latest.zip`: it has its own `HandleImages`/`ImagesPath` handling that stages the folder beside the generated manifest in `bin\Release\FootIk\`, for a repository listing to serve, and the installed copy then has no icon at all since `IconUrl` is not set either. Two fixes in `FootIk.csproj`. A `Content` item with `CopyToOutputDirectory` puts it at `bin\Release\images\icon.png`, which is what a dev-loaded build reads. A `BundleIcon` target then appends it to the finished zip after `DefaultDalamudPackagerRelease`, deleting any existing entry first so repeated builds cannot double it (verified: three builds in a row, one entry). **Overriding the packager instead was rejected**: `DalamudPackager.targets` in the project directory replaces the SDK's default target wholesale (`Condition="… and !Exists('$(PackagerTargetFile)')"`), which would let `HandleImages="false"` through but requires restating all twenty manifest properties, so a property the SDK adds later would silently vanish from the manifest — the same trap as a hand-written `FootIk.json`, for the same reason. Setting `IconUrl` is the one-line alternative and was not taken: it needs the network and a URL that stays valid, where the bundled file needs neither. The packager's staging copy is untouched, so the repository listing keeps working exactly as before.

Skipped: velocity-based plant detection (add only if M3 shows a pop height gating cannot explain), hand/arm IK, syncing results to other players over IPC, per-character profiles.

## Roadmap

- **M0 — Overlay + raycast, no hook (spike part 1).** Read the chain in `Framework.Update` (read-only; last frame's pose is fine), raycasts, world dots, `DebugDrawOffsetY` slider.
- **M1 — Hook + constant knee bend (spike part 2).** Install the render hook; `DebugKneeBendDeg` rotates one knee in the detour. Proves edits survive to render.
- **M2 — Pelvis drop.** Done (2026-09-10) via `GameObject.SetDrawOffset`, confirmed in game; the movement-hook variant stays as an option.
- **M3 — Two-bone raise.** Done (2026-09-10). Terrain height and animation lift are kept apart: feet shift by the terrain under them, the pelvis follows terrain only (keeps run bounce), legs straighten before the pelvis drops, knee angle cap, penetration clamp. Thresholds are fractions of bind-pose leg length. Tried and removed (2026-09-11): the `LegBalance` knob, which lerped the pelvis target between the body's baseline and the average ground under the planted feet so the two legs would "share" a height difference. It was inert at every value, by algebra rather than by a bug: the target is an average of `GroundModelY` over the planted feet, while the reach ceiling `hi` is the minimum of `GroundModelY + MaxExtend` over the same feet, and an average is never below a minimum. `MaxExtend` is `max(0, ...)` against `StraightenLimit`, and a standing idle leg is already straighter than 0.98, so it reads exactly zero and `hi` collapses to the lowest foot's ground. The knob only had room when the lowest foot's leg carried more slack than the feet's height spread — the opposite of the case it was written for. Sinking instead is no share either: below the ceiling both knees fold harder, the high one most of all. The pelvis now follows the planted average, pinned by the same ceiling. Legs only shorten, so a foot up on a rock is paid for by that knee alone.
- **M4 — Foot alignment.** Done (2026-09-10). Normal derived from the hit triangle (the result's `Normal` field reads zero), additive on the animated ankle, capped, fades with height above rest so heel strike keeps its own pitch.
- **M5 — Stairs/ledges.** Done so far: three probes per foot (heel, mid, toe), median height. Tried and reverted (2026-09-10): "higher hit wins" (floats the foot as the toe probe reaches the next tread) and "prefer flat hits over ramps" (did not help on beveled stairs). Open: many staircases are ramps or bevels in collision; see M8. Open (2026-09-10): on natural slopes the feet land ~10 cm below the visible ground, symmetric uphill/downhill, while flat ground is exact. Ruled out: draw-position sink (skeleton transform equals the logical position), root-bone or n_hara pose shift, probe-vs-ankle reference (fixed by evaluating the hit plane under the ankle). Leading suspicion: the collision surface sits below the visual terrain there. Interim: the "slope lift" knob adds raise proportional to slope tangent, as a fraction of leg length like every other distance. Investigate with M8. `DrawOffset` is not sticky (2026-09-11, measured in game, kept): the game clears it whenever it moves a character, a stair step every tread, and `ApplyPelvis` wrote the field only when our own target changed, so after a clear it was never re-asserted and the body drop stood computed but unapplied for most of a climb. It now reads what the field holds, takes our last share off to see what else is in there (nothing, if it has been cleared), puts ours back on top and writes whenever the field is not already that - still only our own share, so SimpleHeels keeps its. `lost peak` on the Status tab is what the two disagree by and belongs at zero; it read a full tread before this and reads zero after. The pose-test knobs that found the `n_root` fault were stripped before release (2026-09-12): saved to the config and overriding the real tilt while non-zero, they were a footgun in a shipped build. The read-only readouts stay - hip height, the draw offset line and the body drop peak (the arm-resolution and hand-over-ground readouts went with `ProbeHands`, 2026-09-12; see M9b). Fixing it did not visibly change the climb, so the snap on true stairs is still open, and the work stopped there (2026-09-11) because almost every staircase in the game is a ramp or a bevel in collision and this only shows on the rare real one. Tried and reverted, all unverified or disproven: `AbsorbStep` with a `StairTau` knob, which accumulated the origin jump as a second additive offset on top of `rawDrop` and counted it twice; carrying the jump across `SmoothDrop` before the easing, on the theory that easing in a frame of reference the game moves in jumps turns a jump of the reference into a lag of the body, which is sound but showed nothing and would have put an untested slope test in the path of every character on every frame; and per-foot smoothing of the ground height, which nobody could see. Note for anyone returning to this: `Body drop raw` reads a correct full tread through all of it, so the arithmetic is not where the fault is, and `Max body drop` is no use as an A/B because `hi` pins `rawDrop` to the planted foot's reach either way.
- **M5b — Edges and narrow supports.** Done (2026-09-11), in-game verified: feet hanging over an edge gather onto the support (joint radial search from both ankles, cheapest uncrossed pair with room between the boots, hold while still, re-plant only when a turn crosses the legs), feet kept out of walls by a boot-sized box, body centred over the feet through the movement hook, a minimum stance sideways and a boot length lengthwise, shallow water looked through to the bed, no gathering while the gate is closed (a fall is flagged as jumping), level support preferred over lower ground within Edge drop unless the character is on an incline (ground half a leg ahead and behind differ by more than a tread, or either foot's hit triangle leans more than about ten degrees); since 2026-09-11 the incline exemption also covers a foot over a drop, because running downhill the leading foot swung out over ground past Edge drop and was gathered back uphill every stride, so only a foot over nothing at all gathers on a slope, and the emote-only body baseline (`ProbeBase`) never used while walking: on a rail the ground under the body is the deck. Open: on a rail the feet must swap ends once per half turn; unavoidable without crossed legs. Narrowed (2026-09-11): the incline exemption asked `OnIncline` of a standing character too, and that reads one height half a leg ahead and one half a leg behind, so it cannot tell a slope from a ledge — at the edge of a crate or a kerb it reports the whole drop, the strongest incline signal there is, and cancelled gathering at exactly the edge that wanted it (reported in game: the feet gathered only once both already stood on the box). It is only ever about a stride, so it is now asked only of a character in motion; standing at an edge the hit triangles (`Sloped`) decide alone. `Block` also grew `Off` and `Settled`, because both silent early returns left the readout saying `None`, which is what a successful gather says. Two gather modes (2026-09-11, awaiting in-game verification): by default the cheapest pair is the smallest move with an edge penalty, and the body slides over the feet, which reads best but hides the logical position - on a rail the visible character stands on the rail while the position may be off it. `GatherToPosition` ("Platforming mode") costs each sample by its distance from `aim` instead, drops the edge penalty, and skips the body move entirely, so the feet straddle the capsule and the body stays on it: what you see under the feet is what you jump from. `aim` is what keeps the pose honest without the body move: the bind stance centre carried to the logical position when both feet search, and the mirror of the other foot about that centre when one of them stays put, so the pair lands centred on the body rather than merely near it (for two feet aiming at one point, the summed square cost is twice the square of the midpoint offset plus half the square of the separation, so centring is already what it buys; the mirror is what extends that to the one-foot case). The narrowing pass is skipped with it, because with one foot fixed it only moves the other and walks the midpoint back off centre. Same trigger as before (a foot over an edge or below level), same hold, same pair rule. Horizontal shift ownership (2026-09-11): the draw object carries exactly what `CharState.MoveWritten` says, and both `MoveDetour` and `ApplyPelvis` may correct it, always by delta. The hook alone was not enough, because it runs only when the game calls `UpdateVisualPosition`: a character standing still kept the shift from the last time it moved, long after the easing had taken the wanted one to nothing. Reported in game as the body standing off the centre of the camera after `/pushups` on a slope, more the steeper the slope, cleared by a second of running - moving is what makes the game call the hook again. Ruled out on the way, from the Status tab: the sit tilt (`On the floor False`, `body tilt 0.0`, and the character never looked tilted, only displaced) and the floor latch (idle hips measured over 0.85, so the release height was always being reached). `StillSpeed` stopped being a setting in the 2026-09-12 cleanup pass: it gates `Hold` and nothing else, it was config-file-only and never on a tab, and it is now the const `StillSpeed` (0.15 m/s) in `Plugin.Tick.cs`. Absolute metres rather than a `*Frac` on purpose, against the rule every other distance follows: world movement speed is the same for every race in this game, so the threshold that separates a character the game is moving from one only its animation is swaying does not scale with leg length. A value hand-edited into an existing config file is ignored from that build on. Stairs (2026-09-12, in-game verified): the `BelowLevel` trigger is gone. It gathered a foot over ground a tread or more below the body even within Edge drop, and standing still on box-collision stairs neither `Sloped` (flat treads) nor `OnIncline` (motion only) exempts it, so every stop pulled the foot over the next tread down back onto the tread the body stands on; the level-first search never offered the lower tread while any level ground was in reach. Now only a foot over nothing or past Edge drop gathers, so Edge drop alone decides between straddling a step and gathering off a kerb, which is what its tooltip already said; lower it under kerb height if the kerb gather is wanted. The incline exemption also no longer applies when both feet hang past Edge drop: a stride hangs one foot, never two, so two hanging feet are a ledge whatever the ground below leans (before, a cliff over sloped ground exempted both). Rounded rails (2026-09-12, in-game verified): reported in game that on a "high precision" rail, a cylinder or a diamond in collision, the gathered feet stood strongly angled. The tilt came from the one hit triangle under the target, and on a faceted rail that is a flank, 45 degrees on a diamond even dead centre, never the surface a flat sole rests on; slope lift added raise from the same tangent. Two changes in `GatherFeet`: a recentred foot takes a straight-up normal, since a boot across a ridge rests level (the along-rail slope of a sloped handrail is lost, which the flank normal was getting wrong anyway); and a sample counts as narrow when an edge lies within two steps on each side along its line, about a boot width, instead of only when it has no standable neighbour at all, because a 5 to 7 cm rail catches two of the 3.4 cm samples and was then never recentred and landed on a flank. The narrow flag is latched with the target (`LatchNarrow`), because a held foot re-reads its normal from the hit under the latched spot every frame and the first build lost the flag the moment the character stood still, so the flank tilt came straight back on a held foot (reported in game, 2026-09-12). `Recentre` probes one step either side to find which sample the edge bisection starts from: two raycasts more per recentred foot, against the Dirs x Steps (160 at default precision) the fan search already spends on that foot in the same frame, so no setting for it; held feet skip both. That last clause was the intent and not the code until 2026-09-12 (found in review, awaiting in-game verification): `narrow` gated the `Recentre` call, and a held foot takes it from `LatchNarrow`, but its kept slot carries the line `-1` — C# gives `-1 % 64` as `-1` and `-1 / 64` as `0`, so the bisection ran from two steps behind the ankle along direction 0, the character's facing, instead of along the rail, and `level` is false for a held foot so ground below the rail passed the support test. Standing on a rail with the other foot hanging and turning on the spot could therefore place the held foot on the deck. `Recentre` is now gated on a real line, which only a fresh candidate has, and `LatchNarrow` supplies nothing but the straight-up normal for a target that has not moved.
- **M6 — Sitting/emotes.** Done (2026-09-11), in-game verified. Whitelist: the gate opens for `CharacterModes.EmoteLoop` as a whole, because the `EmoteMode` sheet gives `ConditionMode` 3 to every looping emote except rows 1–3 (ground sit, chair sit, sleep), which get 11 = `InPositionLoop`; the row id is assumed to arrive in `Character.ModeParam` (⚠ read it off the Status tab). Seated (1 or 3): the leg pass fades out through the ordinary blend, and the whole model-space pose, face and hair partials included, turns about the origin until its up matches the ground plane through four probes half a leg length out (front, back, left, right), capped by `MaxSitTiltDeg`, eased by `SitTiltTau`, and weighted by hip height (nothing above 0.85 of a leg length, full below 0.4) so the sit-down animation settles onto the slope instead of tilting while still upright. Widened from [0.5, 0.25] on 2026-09-11: that window is only the last third of the descent, so the tilt read as arriving after the animation rather than during it. A chair (2) closes the gate: the character is on furniture, not the ground. Feet are not gathered during `EmoteLoop` (2026-09-11): dance stances gathered onto a support read as odd poses; an over-edge foot keeps the animation. Floor emotes (2026-09-11, in-game verified): `/playdead`, `/pushups`, `/situps` are `EmoteLoop`, the mode a dance gets, and the `EmoteMode` sheet does not separate them, so the pose does. They are now treated as ground poses like a ground sit: the gate closes, the leg pass and the body drop fade out, and only the tilt runs. Left on the standing path they floated (`/pushups`) and sank (`/situps`), because a lying body reads as planted feet asking the body up or down, and the pelvis chasing the reps rocked it back and forth. `CharState.HipFrac` (hip model Y over leg length, written each tick after `ReadTransform`) is the test, read a frame late because the gate is computed before the pose resolves; the blend is many frames long, so the lag does not show. `FloorLoop` latches below `FloorHips` (0.4) and releases only above `StandingHips` (0.85), the two ends deliberately apart: `/pushups` swings the hips through any single threshold every rep, and a gate flapping with it faded the legs in and out, which is itself a rocking motion; the mode flips back the frame the get-up animation starts, while the character is still down there, so releasing on the mode handed the standing pass a lying body. The tilt weight is pinned full while a floor emote is actually running, for the same rep reason, and falls back to the hip ramp once the mode leaves `EmoteLoop`, so the tilt leaves with the body on the way up instead of lingering on an upright character. Open: `/doze` on a bed probes the floor under the bed; an equipped weapon does not follow the tilt (2026-09-11, reported in game): weapons are their own draw objects rather than partial skeletons, so `RotateBody` never reaches them and a tilted character wears its weapon at the old angle. hands are not planted, so `/pushups` on a slope rests them wherever the animation puts them (hand IK would be an arm chain through the existing `TwoBone` solver, not a new solver). Hip height is on the Status tab (`hips`), and an idle pose measured over 0.85 there, which is what `StandingHips` assumes; read it before moving either threshold. Never write `n_root` (2026-09-11, found with the Status tab pose-test knobs, in game). `RotateBody` turned every bone of every partial, bone 0 of the body included, and bone 0 is `n_root`, which the game reads back to see how far an animation has carried a character. Turning it turned out to move the character, and the camera re-anchors to where the body lands - not continuously, but whenever the animation changes, which is why it reads as a snap and why it stays put until the next pose change or the first step. Dances travel without doing this because the game moves them deliberately; we were doing it by accident. The turn now skips bone 0 of partial 0 only: bone 0 of a face or hair partial is what fastens it to the head, and leaving that one behind while its children turn tears the head apart (seen in game, both halves). With that, the tilt is back on for prone floor emotes as well as seated ones. Tried and reverted along the way, none of them involved: pivoting the turn under the body's own hips (tested directly with the knob, changed nothing), the floor latch release height, and two passes at the horizontal draw shift. The readouts were honest throughout - `body tilt 0.0` and `Body shift 0.00` after standing up are both true, because by then nothing of ours is applied and the camera is what is out of place, not the character. `Enabled` unticked is the test that pins a symptom on the plugin at all, and it is the one to run first.
- **M6b — Root motion.** Written (2026-09-11), awaiting in-game verification. Dances that carry the root far from the origin (`/tdance`) broke the IK up or down a slope: every step threshold, the pelvis caps and the probe window were relative to the ground at the logical position, while the feet stood on ground far above or below it, so both feet read as a step too tall or as an edge, and the probe start sat below the terrain uphill. Heights are now judged against the ground under the hip midpoint (`Frame.BaseY`, one extra probe per frame; when the window misses, a retry from 1.5 leg lengths up, the character's own headroom, so a bridge overhead is never taken for the floor). The body follows the planted feet, and the baseline is what every step threshold and cap is judged from; the probe window for every foot and gather probe moves with it. `GroundModelY` stays origin-relative, so world heights and the pelvis arithmetic are unchanged.
- **M7 — Other characters + release.** Other characters written (2026-09-11), awaiting in-game verification; the release half is not started. Every field the tick mutated moved out of `Plugin` into one `CharState` per character, held in a dictionary keyed by the character's address and carrying the spawn id, because the allocator reuses addresses. `Frame` carries the state, so each step reads `f.St` and no step signature changed. `Tick` became a dispatcher: the local player first, then the object table walked by index rather than enumerated (`IObjectTable.GetEnumerator` returns the interface and allocates every frame), players and NPCs inside `OthersRadius` yalms, nearest first, up to `MaxOthers` (hard cap 50, off by default), NPCs excluded wholesale rather than filtered kind by kind. Who besides you (`Who`, 2026-09-11): everyone, other players, friends and party, or party only. Relations come from `ICharacter.StatusFlags` (`PartyMember`, `AllianceMember`, `Friend` — Dalamud over the character's own relation byte, the one that draws the nameplate friend icon), read off the object already in hand; no service and no per-patch struct. Ruled out on the way: `InfoProxyFriendList`, which needs ContentId matching and is only populated once the social window has been opened. The budget is a count, not a time slice: the raycasts are the cost and a count bounds them. Gathering is the only part worth a separate knob, because it is the whole spread — walking on flat ground is about fourteen rays a character, a foot over an edge with a 16-direction search is up to thirteen hundred — so `OthersGatherPrecision` (0 = off, the default) rides on `Frame.Dirs` and the `Dirs` property is gone. Wall feelers are the steady-state cost that is left, eight rays a character every frame; split them the same way if the readout says so. A character we hold state for but no longer pick is ticked with the gate forced closed until the blend has carried our offsets back off it, then dropped; one that has left the object table is dropped outright, its offsets gone with it. `ICondition` splits, because it only ever describes the local player: jumping, mounted, swimming, diving and flying gate us alone, while a cutscene or a zone load gates everyone. Others gate on `Mode`, `IsJumping()` and `MoveController.MovementState` (`Normal`/`Flying`/`Diving`, dumped by reflection 2026-09-11). Non-humanoids need no filter: `LegChain.Resolve` matches `j_asi_*` by name, so mounts, minions and monsters fail `Resolved` and are skipped, cached, for free. Open: there is no per-character swimming flag, so a swimmer in water shallow enough for the probe window to reach the bed gets leg IK; an NPC of an eligible kind but a non-human skeleton still holds a budget slot, which is what `Work on` is for; CustomizePlus and SimpleHeels ordering on other characters is unobserved. Still to do for the release: `repo.json` and the publish into `github.com/BSoD38/dalamud-plugins`.
- **M9 — Procedural floor poses.** Contact-fitted orientation written (2026-09-12), awaiting in-game verification. Three attempts paid for the design. Orientation alone can never make anything touch the ground, whatever shape it takes: a share of the turn on each spine bone (reverted) left the back conforming while the hands and feet stayed on the plane the animation assumed, so nothing touched anything. Contact IK alone distorts a limb to serve a target while the rest of the body ignores the world (reverted): a lone wrist solve read as an arm groping for the floor. Layering the two (reverted) buried hands and toes on broken terrain and overextended the arms - the corrections were capped at about three centimetres by their own fade, so the harm was in the solve rather than the targets, `TwoBone` falling back to "bend the way the foot points" for a straight limb, which for an arm bends the elbow forward. The answer was never IK. The orientation was being fitted to the wrong thing: four probes half a leg out from the origin, which sample ground beside the torso, not the ground a prone body lies on. `ContactTilt` now fits it to where the character actually touches - pitch from the hands against the toes over the body's length, roll from the right contacts against the left over its width, each weighted by how near the ground it already is, so a limb held in the air drops out of the fit and an axis with no baseline stays flat. `Solver.GroundTilt`'s four heights and radius reduce to those two slopes, so it supplies the normal, the cap and the finite checks unchanged. Prone only: a seated body has its contacts under itself, where the four probes already sample the right ground, and seated reads well as it is. No limb is solved at all, which removes the whole class of bend-plane and hand-rotation artefacts. Its honest limit: a rigid body cannot touch four points that do not lie on one plane, so on broken ground this is a best fit with residual error, and that is where a small IK cleanup would earn its place - with a real pole hint this time. Fallback if it still reads wrong: `FloorTilt`, on by default, turns the prone tilt off and leaves those emotes to the animation. Stopped here (2026-09-12) at good enough: a rigid body fitted to its contacts is as far as this goes without solving limbs, and driving the whole pose procedurally over the top of the game's animations was judged too ambitious for now. What is left on the table is written above - the residual on broken ground, and the small pole-hinted IK cleanup that would close it.

- **M10 — Bumping into people.** In-game verified (2026-09-12): flinch direction, the size rule against shorter races, and the Gaussian release all checked by the user; tuning history below. Characters have no collision with each other, so the plugin does its own: once per frame, for every ticked character that moves faster than `BumpMinSpeed` with no bump still playing, `FindBump` scans the object table for a Pc/EventNpc on the same floor whose centre is within `BumpRadiusFrac × leg length × (1 + their height / ours)` and which it is closing on faster than `BumpMinSpeed`. Heights come from `Character.Height × Character.Scale` (offsets 0xC8 / 0xC4), the game's own reading; in game (2026-09-12) a male Hrothgar flinched visibly less than the shorter characters it ran into, which only the ratio can produce, so the field does scale with race height; the Status tab prints ours as "body height". Sitting and lying are skipped: `Mode == InPositionLoop` on the other, or `HipFrac < FloorHips` once it is being ticked (a floor emote in `EmoteLoop` on an unticked character slips through). Characters with no `DrawObject`, or with the `Model` bit of `GameObject.RenderFlags` (0x118, `VisibilityFlags`) set, are skipped: invisible quest NPCs were bumped into in game (2026-09-12); `DrawObject.IsVisible` is deliberately not consulted as it may only mean culled. A hit starts an impulse on `CharState` (`BumpAge`, `BumpPush`): a linear rise over `BumpRiseSeconds`, then a Gaussian release `exp(−((t − rise) / BumpTau)²)`, which lingers at the peak where a plain exponential is half gone within a frame (in game the exponential read as weak, 2026-09-12). The push vector's length is the amplitude, `clamp((ratio − 0.4) / 0.3)` for us and the same of `1 / ratio` for them: a body under two fifths of the other's height leaves its torso alone, from seven tenths up it moves it fully, so a Roegadyn running into a Lalafell shoves the Lalafell and does not flinch itself while a Hyur moves a Hrothgar fully. The line was first at half height (`clamp(2 × ratio − 1)`), which left a male Hrothgar at about half strength against a Hyur and a third against a Miqo'te, read in game as the feature being weak. `ShoveTorso` turns it into a spine turn through the generalised `ApplySpineLean` (now a quaternion spread a third per spine bone plus a separate neck quaternion; the slope lean passes pitch and its full counter-turn): the push is split along the body: its fore-aft part pitches the torso about the side axis by `angle × fore`, its sideways part turns it about UnitY by `clamp(−3 × across) × angle` (full from a fifth of a turn off centre, nothing head-on) and leans it about the forward axis by only `BumpSideLean` (0.35) of `angle × across`; the twist is composed innermost (`lean × pitch × twist`, System.Numerics applies the right operand first) so the tip lands exactly along the push instead of being swung round by the yaw. On top of the torso, the whole pose is yawed about the origin through `RotateBody` by `twist × BumpBody × BumpBodyTurn`, where `BumpBody` is the speed at impact over `RunSpeed` (6 m/s) latched on each `CharState` when the bump lands (`CharState.Speed` keeps the last frame.s speed for the bumpee), so a runner is knocked round while a bystander keeps the hit in the shoulders. The legs are then re-solved with `SolveLeg` to the ankle positions recorded before the turn, the ankle orientation turned back (`ankleTilt = q⁻¹`) and the pre-turn hip→knee direction as the pole at full blend, so the hips go with the pelvis and the legs re-bend to reach while the feet keep the stride; letting the feet swing round with the body read as the body sliding round and back (seen in game 2026-09-12). Skipped: a sideways displacement of the whole body through the movement-hook X/Z path — but a displacement *within the pose* was added later and is what makes a standing target read (2026-09-14). The symptom was that being shoved looked wrong only on idle characters while a runner looked right, and the cause is visible in the old control flow: `bodyYaw` comes from `BumpBody`, which for a bumpee is *their own* speed, so a standing one fell out at the `MathF.Abs(bodyYaw) < 0.002f` return and never reached `RotateBody` — or the leg re-solve that follows it. They took the whole hit in the spine with hips and feet nailed down, which reads as folding at the waist. The runner only looked right because the turn gave it that leg re-solve as a side effect. `TranslateBody` (the translation counterpart of `RotateBody`, same `n_root` and partial handling) now carries the whole pose along the push by `BumpShoveFrac` of the leg length, in model space so no scale factor is needed, under the same envelope and amplitude as the angle. Ankles are recorded once and the legs solved back to them afterwards, so **no knee is ever posed**: the hips are carried off the planted feet and the legs below bend because they have to reach, which is the leg recoil without authoring one. Yaw and shove now share that single record-transform-resolve, either or both being applied. Before the split the roll was about `Cross(UnitY, push)` at the full angle, which for a side-on hit is a pure sideways lean from the hips: bystanders, always hit side-on by someone running past, swayed instead of turning (seen in game 2026-09-12); the head goes with the shoulders (a half counter-turn was tried first and read as weak in game) — **reversed 2026-09-14 once the hips moved**: `BumpHeadHold` (1 by default) has the neck undo the spine's turn *and* the rigid yaw, so the character goes on looking where it was looking while the shoulders and hips are carried out from under it. The earlier "weak" reading was taken when nothing but the spine moved, so there was nothing left once the head was subtracted; with the shove displacing the hips there is. It is a slider rather than a constant precisely because that history says the right amount is a matter of taste. The neck sees exactly `turn` accumulated (`Slerp(I, turn, 1/3)` at three spine slots composes back to `turn`), and `RotateBody` afterwards carries the neck with everything else, so the counter is `Inverse(q) * Inverse(turn)` and `bodyYaw` had to move above the `ApplySpineLean` call to be available to it. Face and hair partials need no special handling: `ApplySpineLean` already re-derives each from how its anchor bone moved. The other body takes the opposite push when it already has a `CharState` (Others on), so both flinch in the local client; a seated or floored bumpee is also gated off by its own `active`. Runs after `LeanSpine`, which measures the animated pitch before applying, and before `TiltBody`. Two cooldowns, `BumpCooldown` between any two bumps and `BumpSameCooldown` before the same character (`CharState.BumpTarget`) counts again; a bump landing mid-envelope restarts the rise from the current envelope value (`age = Envelope(age) × rise`) so the angle never drops to zero and pops back. Skipped: arm IK (an additive rotation on `j_ude_a` is the upgrade, never a positional target, which would fight the run cycle's arm swing). Off by default; crowds at aetheryte plazas are the case to watch. `BattleNpc` was dropped from the target filter (2026-09-14, asked for): it is every monster, pet, egi, carbuncle, chocobo companion and trust, and none of them should shove or be shoved. - **M10e — Bumps land on the shoulder line.** Written 2026-09-15, **awaiting in-game verification**; the complaint was that bump detection is "somewhat unreliable" and the fix has two halves, only the second of which was asked for. (1) **The closing-speed gate was the root cause.** `FindBump` required `dot(ours − theirs, dir) ≥ BumpMinSpeed` — the component of the relative velocity along the line between the two centres — evaluated on the frame the gap first drops under `reach`. At that instant the line between the centres points along the contact normal, so for anything but a head-on hit that component is a fraction of the actual speed: with the default 5 m/s against a 6 m/s run, the velocity had to be within 34° of the other body's centre, which admits lateral miss distances up to about 0.42 m out of the roughly 0.76 m at which two bodies of equal height touch. Over half the range of glancing contacts was visibly overlapping and silently dropped. It now tests the full horizontal relative speed `|ours − theirs|` against `BumpMinSpeed` and merely requires the gap to be shrinking (`dot(rel, dir) > 0`), which is what "how fast you are closing on each other" meant all along; `BumpBody` reads that same relative speed, so a side-swipe at a run produces a visible reaction instead of one scaled to nearly zero by the radial component. The `f.Speed < BumpMinSpeed` pre-gate that bounds the object-table walk is unchanged, so with `Shoved` off a bump still needs our own speed over the threshold. (2) **The reference point is the shoulder line, not the point on the floor between the feet** (asked for; the alternative suggestion, the cloth physics mesh, was not taken — walking a foreign character's physics mesh every frame from the render detour is an unbounded pointer walk for a flinch effect, against the never-crash rule, and the cloth work lives in the sibling `ffxiv-cloth-physics` repo). `ShoulderMid` averages `j_ude_a_l` and `j_ude_a_r` model-space translations and puts them in world space through `f.PosAnchor`/`f.Rot`/`f.Scale`, falling back to `ShoulderOverLeg` (1.45) leg lengths straight up the origin for a skeleton whose arms did not resolve. Each ticked character caches it on `CharState.Torso` in `TickOne` beside `HipFrac`, inside the `poseOk` block and so kept fresh whether or not its gate is open; the bump scan reads the other body's from there when something is ticking it, and otherwise estimates it as our own shoulder height above their feet scaled by the existing height `ratio`, which costs no pose walk and is the same answer to within the lean. Both the distance test and the same-floor test now run shoulder against shoulder, so a body one step up a stair is still in reach while one on the balcony above is a torso away and out of it, and a runner's torso leads its feet by however far the animation leans it. `BumpRadiusFrac` deliberately keeps its old meaning — a fraction of the leg length, the two circles merely re-centred — so nothing already tuned has to be tuned again; deriving the radius from the measured shoulder width instead was considered and skipped for exactly that reason, and because shoulder *joints* sit well inside the silhouette the deltoids actually collide with. Velocity is still differentiated from the logical position, never from the shoulder: the torso swings with every stride and differentiating it reads as about a metre a second of noise on a character standing still. ⚠ In game, the things to watch are whether glancing passes now over-trigger (raise `Bump speed` if so), and whether the one-frame staleness of another ticked character's `Torso` — the local player is ticked before the sweep, so their cached shoulder is the previous frame's, about 10 cm at a run — is visible at all.

  - **`FloatSliderNode` quantises to 0.01** — it stores the value as `(int)(v * 100)`. `StraightenLimit` (0.90–0.999), `RestAdjustFrac` and `SlopeLiftFrac` all need a finer step, so every slider is the integer `SliderNode` carrying *steps above the setting's own minimum*: `slider = round((value - min) * scale)`, `value = min + slider / scale`. ## Simplification pass (2026-09-16)

A repo-wide audit for over-engineering, applied in full. Nothing here changes what the plugin does, and none of it is
in-game verified: it is a clean build and a read, and the whole of it touches the render path in three places.

- **The mesh diagnostics are gone**, recorded under M8 above along with what it costs.
- **`RotateBody` and `TranslateBody` were the same walk over every partial, one line apart**, and `ShoveTorso` called
  both in sequence — two full pose walks where one does. `MoveBody(skel, pose, q, by)` rotates about the origin and
  shifts in the same pass, which is the order the two calls had. The `n_root` rule and the partial-anchoring rule are
  unchanged and still carry their comments.
- **`ProbeFoot`'s three-hit sorting network is `cand[..n].Sort(ByHeight)`**, over a cached `Comparison<RaycastHit>` so
  the render thread allocates nothing. Same median, same "two hits take the lower".
- **One tab table replaces three structures keyed by tab index** (`TabNames`, `TabFields`, and `ShowTab`'s switch).
  Adding a tab is one row. Per-tab reset stays: dropping it would have cut the `nameof` lists, which is most of the
  lines, but "Reset tab" is worth more than the lines.
- **`Refresh`'s four parallel lists are two**, each carrying what it used to keep in a list beside it, walked through
  `CollectionsMarshal.AsSpan` so the tuple can be updated in place.
- **`Settings.Reset` and `Repair` share one reflection walk** over a predicate.

Left alone deliberately: `Solver.SelfTest` (the only automated check this repo has), the `ResolvePose` guard chain, the
delta-only draw-offset bookkeeping, and the Status tab's Details fold and world markers — in-game is the only way
anything here is verified, and those are the instruments.
